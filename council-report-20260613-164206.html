Council Report — eu-regulations MCP Server

Question: Is the eu-regulations MCP server ready to launch? What are the critical gaps, risks, or opportunities before it goes public?
Free, read-only, no-auth HTTP MCP server · 3 EU regulations indexed · 12 tools · Target: compliance professionals + agent developers

Chairman's Verdict

Where the Council Agrees

Five out of five advisors flagged the same three problems independently: the citation rule is unenforceable, rate limiting is absent, and the corpus is unvalidated. When every perspective — including the one explicitly assigned to find upside — converges on the same failure modes, those are real blockers, not matters of opinion.

Every advisor said the same thing in different words: a compliance professional who acts on wrong, stale, or hallucinated-but-cited information faces real consequences, and the current architecture provides no protection against that. The SKILL.md citation rule is a disclaimer dressed up as a safeguard.

Citation rule is unenforceable at the server layer
No rate limiting = operational timebomb
Cross-regulation edges not legally validated
No defined failure mode / "what does wrong look like?"
Corpus staleness is a liability, not just a UX issue
v1 corpus scope (3 acts) is reasonable for launch

Where the Council Clashes

Expansionist

No-auth, free model is a distribution weapon. Launch now. The knowledge graph is the moat. Every agent builder who integrates becomes a dependent.

Contrarian + First Principles + Outsider + Executor

Same model is an operational timebomb and liability surface. No rate limiting, no corpus validation, no failure mode defined.

Resolution: Both are right but describing different time horizons. Fix the floor, then exploit the moat. The disagreement dissolves when you sequence it correctly.

Second clash: Is the 1427-edge knowledge graph a moat or the biggest unvalidated assumption? The Contrarian and First Principles advisor say the latter. This has a concrete answer — someone needs to produce it before launch.

Blind Spots the Council Caught

Blind Spot 1 — Corpus Versioning

The regulations have version identifiers — OJ publication dates, corrigenda, amendment acts. If the server returns content from a superseded article version without surfacing that, the EUR-Lex citation requirement becomes actively dangerous. A compliance professional citing "Article 9 of the AI Act" needs to know which version they are citing. Not addressed anywhere.

Blind Spot 2 — Laundered Hallucination via MCP Transport

None of the five advisors asked what happens when Claude's MCP client misparses a tool response, retries a failed call, or silently drops a result mid-reasoning chain. The actual risk is not uncited responses — it is laundered hallucination: an agent skips a result, fills the gap from training data, and still produces a confident, EUR-Lex-cited answer the user cannot distinguish from real retrieval.

Blind Spot 3 — MCP Client Fragmentation

Claude Code, Claude Desktop, and VS Code Copilot each implement MCP differently and update independently. No versioning, no protocol compatibility matrix, no client-specific testing. A free server fragile against the very distribution channel it depends on. The compliance professional never sees raw tool output — an agent does. Malformed responses or ambiguous tool descriptions fail invisibly.

The Recommendation

Verdict

Not ready to launch to compliance professionals as the primary target. Ready to launch to developers as a beta with explicit caveats.

The gap is not technical capability — the corpus scope, 12-tool surface area, and cross-regulation graph are credible for a v1. The gap is the trust infrastructure required to serve the stated user.

Launching to developers first is not a retreat — it is the correct sequencing. Developers will surface MCP client compatibility bugs, malformed tool responses, and edge case failures before a compliance professional ever sees them. That is free QA on the hardest problem.

Three things before any public launch:

  1. Add corpus version metadata (OJ publication date, last sync timestamp) to every tool response payload — as a returned field, not documentation.
  2. Enable rate limiting on the Traefik route. Two hours of work. No argument.
  3. Run every tool against adversarial inputs across all three MCP clients and document what breaks. Publish a compatibility matrix.

The One Thing to Do First

First Action

Put the corpus version and last-sync timestamp into every single tool response payload as a returned field — not in documentation, not in SKILL.md, not as a README note. In the payload. Every other safeguard depends on the user knowing whether what they are reading is current. Right now they cannot know that. Close that gap first.

Advisor Responses

The Contrarian

Three critical problems before this goes live.

The citation rule is unenforceable and creates liability, not protection. "Every claim must cite EUR-Lex" is a prompt instruction in a SKILL.md file. Claude can and will hallucinate citations, cite the wrong article, or paraphrase incorrectly while attaching a real-looking EUR-Lex URL. Compliance professionals who rely on this for actual regulatory work and get a wrong citation face real consequences. The server has no mechanism to verify that what Claude says matches what the tool returned. The citation rule gives false confidence.

1427 edges and 36 dimensions sounds impressive until you ask: validated by whom? The knowledge graph was built programmatically. Who confirmed the cross-regulation edges are legally meaningful? A dimension-mediated edge between GDPR Article 22 and AI Act Article 9 might be spurious pattern-matching. Lawyers using this for compliance work will find one bad connection and distrust the entire corpus.

"No-auth, free, read-only" with no rate limiting is an operational timebomb. The first time someone builds a scraper or a bulk embedding job against it, the server goes down. "Free" is fine; "unprotected" is not. When it's down, the SKILL.md tells agents to call it — they'll fail silently or with unhelpful errors.

The opportunity hiding in these gaps: a disclaimer layer that surfaces tool output verbatim alongside any synthesis, plus a confidence/provenance field per result. That's the difference between a toy and something compliance teams can actually cite in an audit. Not ready. Fix the liability surface first.

The First Principles Thinker

The question assumes "launch readiness" is the right frame. It isn't. The real question is: what job does this server do, and does anything prevent it from doing that job?

What does a compliance professional actually need? (1) Trust that the information is current and authoritative. (2) Ability to act on what they find. (3) Confidence the tool won't silently mislead them.

Gap 1: Corpus staleness is existential, not operational. The EU AI Act has implementing acts, delegated acts, and guidance trickling out continuously. A stale corpus doesn't just reduce utility — it creates liability. When did these documents last sync? Is there a sync mechanism at all?

Gap 2: The 12-tool surface area solves a problem users don't have. Compliance professionals don't want to orchestrate 12 tools. They want answers. The complexity lives in your system, not theirs.

Gap 3: "Read-only, no-auth" is a feature statement, not a trust statement. Who maintains this? What's the SLA? When it returns wrong information (it will), what's the correction path? The SKILL.md citation rule implies Claude is responsible for accuracy. That's wrong. The server is responsible.

The actual launch blocker: You haven't defined what "wrong" looks like and how you'll catch it. Until you have a correctness monitoring mechanism, you're not launching a compliance tool — you're launching a confidence trap.

The Expansionist

This is undervalued as a platform, not just a tool. What you're actually sitting on is the infrastructure for a living regulatory intelligence layer.

The corpus is the moat, not the server. 1427 edges and 652+ domain-concept nodes across three acts is non-trivial curation work. The question before launch isn't "is the server ready" — it's "how fast can you index NIS2, CRA, DORA, DSA, DMA?" Every regulation you add increases the value exponentially because cross-regulation edges compound. Users don't want three regulations — they want the EU regulatory graph.

The no-auth, free model is a distribution weapon. Every AI agent builder who integrates this becomes a dependent. Once you're in their agent stack, switching cost is high. This is land-and-expand at the infrastructure layer.

The SKILL.md companion is underrated. You're shipping a cognitive interface contract, not just an API. Formalize it — version the SKILL.md alongside the server, publish a changelog, make it something agent builders can pin.

The critical opportunity before launch: publish a public roadmap of which regulations are coming next. The roadmap is what turns a tool into a platform.

The Outsider

The product description is written for someone who already knows what it is. "12 tools," "1427 graph edges," "652+ domain-concept nodes" — these numbers mean nothing to a compliance professional. The framing is engineer-to-engineer, not engineer-to-buyer.

The corpus gap is invisible. A first-time user has no way to know what's missing until they ask a question and get a confident-sounding answer about something you haven't indexed. That's a professional liability for the compliance officer citing your output to their board.

"No-auth, free, read-only" sounds like a prototype. Legal ops teams expect rate limiting, SLAs, and audit trails. The absence of auth is a feature to a developer and a red flag to a compliance team's IT security.

The citation rule is load-bearing but unverifiable. If a regulation was amended after indexing, the citation rule creates false confidence rather than preventing it.

The biggest gap: there's no failure mode described anywhere. What does the system say when it doesn't know? Until that's answered, launching to compliance professionals is premature.

The Executor

Three concrete things blocking Monday launch, ranked by how fast they'll hurt you:

1. Rate limiting is not mentioned anywhere. A free, no-auth HTTP endpoint with no rate limiting is a free DDOS target. This takes two hours. Do it first.

2. You have no error baseline. The report_error tool collects errors — but right now you have zero traffic, so you have no idea if the 12 tools actually work end-to-end under real agent usage. Run Claude Desktop against every single tool with adversarial inputs. Log every failure. Fix what breaks. Half a day of work.

3. The SKILL.md citation rule has no enforcement path. Add EUR-Lex URLs directly into every tool response payload so the citation is automatic, not optional. One-sprint fix but it's the difference between a professional tool and a liability.

What's actually ready: the corpus scope (3 acts, cross-regulation graph) is reasonable for a v1. The 12-tool surface area is coherent.

First step Monday: enable rate limiting on the Traefik route. Everything else can follow, but that one can't wait.

Peer Review Highlights

What the reviewers said

Strongest response (4/5 votes): The First Principles Thinker — for reframing around user jobs-to-be-done, the "confidence trap" diagnosis, and forcing the builder to define what "wrong" means before shipping.

Biggest blind spot (5/5 votes): The Expansionist — for treating the corpus as a moat and the no-auth model as pure upside without any operational risk calibration. "Optimism without risk calibration is not strategy, it's cheerleading."

Universal miss across all five advisors:

  • Corpus versioning: OJ publication dates and amendment provenance are not surfaced in responses — making every citation potentially stale.
  • MCP transport as silent failure mode: Tool responses can be misparsed, retried, or silently dropped. Laundered hallucination is harder to catch than a missing citation.
  • MCP client fragmentation: Claude Code, Claude Desktop, and VS Code Copilot implement MCP differently. No compatibility matrix exists.
